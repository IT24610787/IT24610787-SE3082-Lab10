EXERCISE 4 - Multiplying two 3D matrices element by element

Size: 500 x 500 x 500 = 125,000,000 elements (500 MB per matrix).
The sheet's original 10,000 per dimension would be 10^12 elements
(4 terabytes per matrix), far more than a Colab GPU can hold.

Launch: 8 x 8 x 8 = 512 threads per block, grid of 63 x 63 x 63 blocks
(500 / 8 = 62.5, rounded up to 63 in each dimension).
Total threads = 128,024,064, which is more than 125,000,000, so the
guard checks x < nx, y < ny AND z < nz.
Flat index: (z * ny + y) * nx + x.
16 x 16 x 16 would be 4096 threads per block, over the limit of 1024.

Result:
Grid: 63 x 63 x 63 blocks
C[499][498][0]   = 76 x 15 = 1140   (first of the last 1000)
C[499][499][499] = 47 x 68 = 3196   (last result)
Verification: 0 mismatches out of 125000000
Time taken - 0.0079250 s

THINK: 3D (Exercise 4) vs 2D (Exercise 6 from Lab 9)
Exercise 6: 100M elements in about 0.00508 s.
Exercise 4: 125M elements in 0.00793 s, about 0.0063 s per 100M
elements, so the 3D kernel was somewhat slower per element (about 25%,
from a single run).
The arrangement of threads matters little because each element needs
just one multiply, so the program is limited by memory speed, not
arithmetic. It still matters a bit: a warp is 32 consecutive threads.
In a 32 x 16 block a warp reads 32 neighbouring values in a row, but in
an 8 x 8 x 8 block it covers only 8 consecutive values across several
rows, so its memory reads are less efficient. This is my likely
explanation and I did not test it. The extra idle threads in the 3D
grid (about 2.4%) are too few to explain the gap.
